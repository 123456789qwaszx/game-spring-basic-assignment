# M2. 게임 생성과 입력 검증

## 목표

POST /games를 요청부터 DB까지 완성한다.

## 이번 단계에서 이해할 것

DTO, Bean Validation, 쓰기 트랜잭션

## 시작 조건

M1의 결과와 남은 문제를 확인한다. 선행 실행 기반이 막히면 독립 작업만 진행하고 완료 판정을 미룬다.

## 구현 순서

- [o] CreateRequest·RunCardRequest와 CardResponse·GameDetailResponse를 작성한다.
- [o] playerName은 공백 금지·2~12자, deck은 비어 있지 않게, 내부 카드 검증을 연결한다.
- [o] cardType은 공백 금지 String, acquiredFloor는 Integer·필수·0~10으로 검증한다.
- [o] 쓰기 트랜잭션에서 Game 저장 → 요청 순서대로 카드 저장 → 카드 ID 오름차순 조회 → 상세 DTO를 조립한다.
- [o] Game 초기값은 99·1·REWARD·PLAYING. 시작 덱은 POST 요청을 저장하고 서버에서 9장을 만들지 않는다.
- [x] POST /games를 201로 연결하고 기존 ErrorResponse·400 핸들러를 유지한다.
(201은 아직 미연결 400핸들러 유지만.)

## 내가 설명할 수 있어야 함

### 요청 DTO·Entity·응답 DTO의 역할은?
- 요청 DTO는 외부 입력 받고 검증
- Entity는 DB 상태 표현
- 응답 DTO는 클라에 전달할 형태

### @Valid와 필드 제약은 어떻게 함께 동작하는가?
- @Valid없이 제약만 붙여두면 조용히 통과함.
- DTO에서는 무엇이 유효한지 선언,
- @Valid는 Controller에서 언제 검사할지 지정.

실행 순서:
1) Jackson(@RequestBody)이 JSON -> DTO 역직렬화
2) @Valid를 보고 Bean Validation(카드 제약) 실행
3) 위반한게 있으면 MethodArgumentNotValidException
4) 차후 GlobalExceptionHandler가 ErrorResponse로 변환
5) (통과 시에만) 메서드 본문 실행

### 생성과 카드 저장을 하나의 트랜잭션으로 묶는 이유는?
- Game과 RunCard 저장을 하나로 묶어 일부만 저장되는 불완전한 회차 방지
