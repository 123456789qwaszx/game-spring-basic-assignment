# M4. 진행과 전체 덱 저장

## 목표

PUT /games/{gameId}/progress로 진행과 전체 덱을 함께 저장한다.

## 이번 단계에서 이해할 것

트랜잭션, 영속 상태 변경, 전체 덱 교체

## 구현 순서

- [o] ProgressRequest의 HP 0~99·층 1~10·필수 phase/status·비어 있지 않은 deck을 검증한다.
- [o] 게임 조회 → 진행 필드 변경 → 기존 카드 삭제 → 요청 전체 덱 저장 → 상세 DTO를 작성한다.
- [o] 위 작업 전체를 public Service 메서드 하나의 쓰기 트랜잭션으로 묶는다.
- [o] Game ID와 이름을 유지하고 새 카드 ID를 응답한다.
- [o] 같은 PLAYING 요청을 반복하여 카드 수·내용·순서를 확인한다.

## 질문

### 왜 전체 덱 교체인가?
3) 덱 전체 교체 vs 카드 개별 수정

전체 교체:
- 저장 할 때마다 모든 카드 DELETE/INSERT
- 카드 ID가 매번 바뀜.
- 카드 수가 많으면 비효율적.

- 현재 클라가 전체 덱을 전송함
- 카드 ID를 외부에서 참조 하지 않음
- 정확한 최종 상태 저장 보장.

카드 개별 수정을 구현한다면,
- RunCardRequest에 카드 ID가 들어가야함.
- 그걸 토대로 서버가 비교:
 1) 기존에 있고 요청에도 있음 -> 유지 또는 수정
 2) 기존에는 있고 요청에는 없음 -> 삭제
 3) 기존에는 없고 요청에만 있음 -> 추가

- 기존 카드와 요청 카드 매칭
- 추가/유지/삭제 분류
- 중복 ID 검증
- 다른 Game의 카드 ID 구분
- 누락과 위조 처리
- 개별 카드의 정체성 관리

위와 같이 로직과 개념이 추가됨.

장점
- 기존 20장을 20DELETE, 20INSERT 대신 변경된 카드만 처리 할 수 있음.
- 카드별 이력을 남길 수 있어 버그나 통계 조사에 유리.
- 강화, 합성 등 동작별 API 추가 가능.
- 카드 ID가 유지되기에, 참조 가능해짐.

- 현재는 덱 크기가 작고, 게임 기획 상 개별 ID 관리가 필요없다고 판단 됨.

### 조회한 Game 변경에 save가 반드시 필요한가?
- Hibernate가 더티체킹을 수행해서.

- Transactional 에서 findById로 Game을 조회했을 때,
- 이 Game Entity는 영속성 컨텍스트가 관리한다.
- 이때 Hibernate가 조회 시점의 필드 값을 스냅샷으로 보관 함.
- 즉 game의 필드값을 바꿧을 때 스냅샷과 현재 값이 달라짐.
- 트랙잭션 커밋 시, Hibernate가 flush를 수행하며 관리 중인 엔티티들의 스냅샷과 현재값을 비교하고, 달라진 필드에 대해 UPDATE를 만들어 실행한다.
