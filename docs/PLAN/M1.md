# M1. 도메인과 DB 관계

## 목표

Game·RunCard의 단방향 관계와 테이블을 이해한다.

## 이번 단계에서 이해할 것

Entity, PK·FK, IDENTITY, 단방향 ManyToOne

## 시작 조건

M0의 결과와 남은 문제를 확인한다. 선행 실행 기반이 막히면 독립 작업만 진행하고 완료 판정을 미룬다.

## 구현 순서

- [o] 기존 GamePhase·GameStatus·Game·RunCard를 같은 패키지에서 직접 작성한다.
- [o] Game의 IDENTITY ID, 문자열 enum, JPA용 기본 생성자, 초기값 생성자를 확인한다.
- [o] RunCard → Game에 LAZY·optional=false·game_id FK를 둔다. Game에 카드 컬렉션은 추가하지 않는다.
- [o] 기존 Repository 계약을 유지한다. 아직 필요하지 않은 계층·인터페이스를 확장하지 않는다.
- [o] MySQL의 두 테이블·FK를 확인하고 관계를 그림이나 문장으로 기록한다.


## 질문

### @Entity가 필요한 이유
- Java 클래스가 JPA가 관리할 영속 객체임을 나타냄. 
- 이게 있어야 Hibernate가 테이블 생성 대상으로 인식

- 기동 시 Hibernate가 필드를 읽어 테이블 스키마를 결정
  (ddl=auto=update가 이 정보로 테이블을 만들었음.)
- @Id 필드가 반드시 있어야 함

### @Table(name = "games")가 필요한 이유
- 테이블 이름을 명시. 이게 없으면 Hibernate 기본 전략에 따라 클래스 명 Game이 game(단수)가 됨.
- 현재 기획 명세상 REST 자원을 복수형으로 다루는 중.

### @NoArgsConstructor(access = AccessLevel.PROTECTED)
- 기본 생성자는 JPA명세가 요구하기 때문에 있어야함.
- Hibernate는 DB에서 행을 읽어올 때 리플렉션으로 빈 객체를 먼저 만들고, 그 다음 필드에 값을 채워 넣음.
- 만약 인자가 없다면 빈 객체 생성이 불가능.


### @ManyToOne

>@ManyToOne  
private Game game;
- RunCard가 하나의 Game에 속할 수 있다는 뜻.

- 단방향 참조
runCard.getGame(); // 가능
game.getRunCards(); // 컬렉션이 없으므로 불가능.
- 이 플젝은 카드만 따로 탐색하는 요구가 없고, Repository에서 게임 회차 별 카드를 조회하기 때문에 미구현.

**LAZY**
>fetch = FetchType.LAZY
- RunCard를 조회했다고 하더라도, 연관된 Game의 모든 필드를 즉시 조회할 필요는 없음.
- 실제 game 데이터가 필요할 때 조회하도록 지연시킴.

**optional = false**
- JPA 객체 관계에서 게임이 없는 카드는 허용하지 않는다는 의미.

**nullable = false**
- DB의 game_id 컬럼에도 NULl을 허용하지 않는다는 의미.

### @Index
- run_cards 테이블에 생성할 인덱스를 지정하는 속성
- @Table의 indexes는 배열을 받을 수 있으므로, 인덱스가 여러 개라면 다음처럼 작성.

@Table(
    name = "run_cards",
    indexes = {
        @Index(
            name = "idx_run_card_game",
            columnList = "game_id"
        ),
        @Index(
            name = "idx_run_card_created_at",
            columnList = "created_at"
        )
    }
)

- 현재는 인덱스가 하나뿐이기 때문에 중괄호를 생략한 형태
@Index(
    name = "idx_run_card_game",
    columnList = "game_id"
)
- game_id 컬럼을 기준으로 인덱스를 만들겠다는 의미

>name = "idx_run_card_game": DB에 만들어 질 인덱스의 이름.  
(idx = index / run_card = RunCard 테이블 / game = game 기준 인덱스)

> columnList = "game_id"  
- 인덱스를 적용할 DB 컬럼 이름을 지정
- 여기에는 Java 필드 이름인 game이 아니라 실제 테이블의 컬럼 이름인 game_id를 적어야 함

**현재까지의 흐름을 정리하면**
Java 필드: game
| @JoinColumn
DB 컬럼: game_id
| @Index
DB 인덱스: idx_run_card_game


- Hibernate의 스키마 자동 생성 기능이 적용되면 개념적으로 다음과 같은 SQL이 실행됨
```sql
CREATE INDEX idx_run_card_game
ON run_cards (game_id);
```

## 질문

### Hibernate란?

지금 프로젝트의 층을 보면,
Spring Data JPA (: 레포의 인터페이스를 편하게 쓰게 해주는 층)
|
JPA (: 명세. @Entity, @Id, EntityManager 등을 정의)
|
Hibernate(: 그 명세의 구현체. 실제로 SQL을 만들고 실행)
|
JDBC -> MySQL

- 이전 lv4에서 @Transactional(readonly = true)로 해놓고, Hibernate가 INSERT 실행하려다 거부 당함

- 이전 lv7에서 List<Game> findAllByOrderByIdDesc();
이건 Spring Data JPA가 이름을 파싱해 JPQL을 만들고, Hibernate가 그 JPQL을 MySQL방언에 맞는 SQL로 번역함.
- 노트에 적어뒀던 "SELECT * FROM games ORDER BY id DESC;"이 최종 SQL이 Hibernate의 출력물.

- 이전 lv8에서 더티 체킹과 flush 동작.
- 트랙잭션이 커밋될 때, Hibernate가 flush를 수행, 관리 중인 엔티티들의 스냅샷과 현재값을 비교했음.
- 따로 save()를 부르지 않았음에도 UPDATE가 나가는 건, Hibernate가 조회 시점 값을 복사해 들고 있다가 커밋 직전에 비교했기 때문.
- 이 스냅샷 저장소가 영속성 컨텍스트이고, Hibernate 안에 있음.

- 즉 Hibernate란, JPA의 명세를 토대로 실제 SQL을 실행하는 엔진.

### Game과 RunCard의 참조 방향을 코드와 FK로 설명하면?
> RunCard  
@ManyToOne(fetch = FetchType.LAZY)  
@JoinColumn(name = "game_id", nullable = false)  
private Game game;

> Game  
RunCard를 가리키는 필드가 없음

> 과제 공통 조건  
엔티티 연관관계는 단방향으로만 사용합니다. cascade, orphanRemoval, 양방향 컬렉션은 사용하지 않으며, 자식(RunCard)의 조회·저장·삭제는 Repository를 통해 명시적으로 처리합니다.

- FK는 항상 자식 테이블에 있음
game.id <- run_cards.game_id(FK)

### JPA용 기본 생성자와 초기화 생성자의 역할은?
- 두 생성자의 호출 주체가 다름.
- @NoArgsConstructor(access = AccessLevel.PROTECTED) // Hibernate가 호출
- public Game(String playerName) { ... }             // 우리 코드가 호출

- Lv7에서 저장된 여정을 불러올 때 Hibernate가 하는 일
1. SELECT * FROM games WHERE id = 5
2. 리플렉션으로 빈 Game 객체 생성   <- 기본 생성자 필요
3. 각 필드에 조회한 값 주입

- 왜 둘다 필요한가? - 자바 문법 문제.
생성자를 하나라도 직접 정의하면 컴파일러가 자동으로 넣어주던 기본 생성자가 사라짐.
Game(String)을 만들었으니 Game()을 명시적으로 다시 추가.

### 카드 ID와 game_id는 각각 무엇을 식별하는가?
**run_cards.id**
- id는 PK 전 테이블 유일. 이 행이 무엇인지.

**run_cards.game_id**
- game_id는 FK. 유일하지 않고, 이 행이 누구의 것인지.
