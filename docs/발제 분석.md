## 0. 빵꾸들의 목적
- LV2. @Service 누락: 
부팅 실패 로그를 읽고 원인을 특정할 수 있나.

- LV3. /game + GET없음 -> 405:
405와 404의 차이를 아나. REST에서 URL이 자원인 지를 아는지.

- LV4. 쓰기에 readOnly = true:
트랙잭션이 무엇인지 아는지.

- LV5. 빈 CardResponse:
명세를 코드로 정확히 번역할 수 있는지.

- LV6. 주석 처리 된 컨트롤러:
PUT의 의미(전체 교체)를 아는지.

- LV7. 레포지토리 메서드 없음:
스스로 찾아서 만들어 보기.

- LV8. 더티 체킹 / 삭제 순서:
영속성 컨텍스트가 언제 어떤 동작을 하는지.


## 1. 나의 현재 상황
- 개념적으로는 알고 있지만, 실제 작성 경험이 없음.
- 따라서 빈 파일에서 그저 하나하나 따라 쳐보는 것부터 해보는 게 좋다고 생각함. 나 스스로 그게 재밌기도 하고.

- 다만 그렇게 아예 처음부터 rewrite를 하게 될 경우, 빵꾸난 것들을 진단하는 경험을 할 순 없음.
- 그럼에도 자바와 스프링 경험이 없는 것을 인정하고, 이런 테스트를 치르는 것은 나에게 도움이 되지 않는 다고 판단.

- 대신에 명세를 토대로 아예 처음부터 하나씩 쳐보되, 주요 빵꾸 지점에서 코드를 왜 그렇게 썻는지 정리.

## 2. 명세 분석

### 2-1 체크포인트 저장 서버:
- 계산은 클라. 서버는 저장만 함.  
즉, DTO 형식만 맞으면 값의 타당성 검증은 굳이 하지 않음.
- 그럼에도 초기값은 서버가 정함.

### 2-2 서버 저장 어휘:
**Game**
- 여정: `Game`
- id: `Long` | AUTO_INCREMENT
- 플레이어 이름: `playerName` | 2~12자
- 현재 체력: `currentHp` | 0~99
- 현재 위치한 층: `currentFloor` | 1~10
- 단계(층 안에서 멈춘 지점): `phase` | enum 3
- 상태(여정의 결과): `status` | enum 3

**RunCard**
- 카드: `RunCard` -> `Game`을 `@ManyToOne` 단방향 참조
- id: `Long` | AUTO_INCREMENT
- 카드 타입: `cardType` (String) | 해석 없는 string
- 카드 획득 층: `acquiredFloor` | 0~10

**덱(deck)**
- 응답 DTO에만 존재하는 개념.
  `RunCardRepository`로 따로 조회해서 조립.
- 시작 덱: 여정 시작 시 기본 9장, 전부 `acquiredFloor = 0`

### 2-3 게임 루프
>"->"마다  
 PUT/progress 날아옴.

시작 버튼 클릭  
(**POST /games 여기만 POST**.  phase=REWARD 로 초기화)  
->[1]REWARD(시작 보상 선택)  
->[2]BATTLE(그 층의 전투)  
->[3]REWARD(전투 보상 선택)  
->[4]BATTLE(다음 층)  
...10층까지...  
->[10]FINISHED + CLEARED  
 or FINISHED + FAILED (도중 HP 0)
